# 索引优化：先读执行计划，再看快了多少

索引实验围绕客户、地块和关联表展开。要求并不是看到慢查询就加一个索引，而是先记录执行计划，再说明为什么选某些字段，最后比较变化。

## 索引对应的是访问方式

先看查询按什么过滤、怎样连接、是否排序，以及预计返回多少数据。不同查询需要的访问方式可能不同，不能只给每一列都建索引，然后把所有变化归功于“有索引了”。

表很小、需要返回大部分记录时，顺序扫描可能是合理选择。有没有使用索引，不应成为判断执行计划好坏的唯一标准。

## 估计与实际放在一起看

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT lot_id, lot_value
FROM lot
WHERE lot_district = 2;
```

示例中的 `ANALYZE` 会实际执行查询，并提供实际行数与时间；`BUFFERS` 帮助观察缓冲区访问。它不同于仅查看估计计划。针对会修改数据的语句使用时，更要清楚执行会产生实际效果。[PostgreSQL 官方说明](https://www.postgresql.org/docs/current/sql-explain.html)

比较前后计划时，可以看估计行数与实际行数差距、扫描方式和总耗时。导入大量数据后更新统计信息，也有助于优化器作出更符合当前数据的判断。

## 不用一次计时概括全部表现

缓存、数据规模、后台任务和查询返回范围都会影响耗时。对照实验尽量保持条件一致，记录索引定义与执行计划，而不是只截一个更小的毫秒数。

本篇保留实验方法，没有重新运行原始数据，因此不宣称某个索引带来确定倍数的提升。优化的价值在于能解释变化，而不只是让结果表格看起来更漂亮。
