CloudChat 的留存材料既有项目计划，也有登录、注册、好友和文件上传的业务说明。整理时能看到一个共通点：每个按钮背后，都要有客户端和服务端共同理解的一种消息。

## 先区分操作与结果

“用户点击发送”只是本地动作，“服务端收到”“内容已保存”“接收方已获得”是不同阶段。界面如果把它们都压成一个成功提示，就很难处理网络中断或服务端失败。

消息至少需要表达请求类型和必要数据，响应则要能说明成功与否。进一步设计时，可以加请求标识，让返回结果对应到正确的那次操作，避免并发请求混在一起。

## 业务状态要和连接状态分开

网络连接存在，不代表已经登录；登录成功，也不代表任何操作都允许。客户端可以改善交互，服务端仍要检查身份和权限。

聊天消息还会遇到重复、乱序和重连。即使学习项目暂时不做完整处理，也应在设计说明里承认这些边界，避免把一个顺畅样例当作全部情况。

## 项目计划不能替代完成证据

README 写了从选题到联调的日期安排，还列出文件传输、视频通话等任务。但一张计划表只说明预期，不能据此宣称所有功能都已完成。公开回顾更适合围绕已有代码与业务说明，写清可确认的部分。

我最想保留的是协议意识：客户端和服务端不是靠按钮名称自动理解彼此，而是靠清楚的数据结构、状态和错误约定协作。界面越简单，背后的约定越值得写明白。
