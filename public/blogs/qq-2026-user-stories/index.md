# 用户故事写完以后，还要能判断它是否完成

“机器医声”课程项目关注设备声音采集、质量检查、异常评分和后续复核。讨论二把需求写成用户故事，再补上验收测试，这一步让原本宽泛的功能名称变得更具体。

## 故事不只是把功能换一种说法

“支持上传”只说明一个动作。“作为巡检人员，我要提交设备录音，以便进入后续分析”，则交代了角色与目的。随后还要明确：录音与哪台设备、哪个工况关联，信息不全时怎么办。

用户价值不是装饰语，它可以帮助判断哪些信息必须保存，哪些交互是核心链路的一部分。

## 给定、当、那么

可以用三段描述一个可检查场景：给定录音文件有效且设备信息齐全，当上传完成，那么系统应记录质检状态并进入下一步。再补一个失败场景：缺少设备编号时，提示补全，不直接生成评分。

只写成功路径，往往会漏掉系统真正容易混乱的部分。网络中断、文件损坏、质量不合格，都应有明确去向。

## 数值目标不等于已实现结果

材料中有响应时间、评价指标和误报率目标。这些可以成为验收条件，但在测量前只能称为目标。需要固定输入、环境、数据划分与统计方式，才能在以后判断是否达到。

异常分数也不是设备故障的最终结论。项目流程安排了人工复核和工单处理，使模型输出能够进入业务判断，而不只是停在一个数字。

这一轮文档工作提醒我，需求写清楚的标志之一，是别人能够据此准备测试，并知道什么结果算通过。故事描述价值，验收标准把价值落到一次可以检查的行为上。
